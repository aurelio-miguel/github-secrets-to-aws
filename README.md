# GitHub Secrets to AWS

Sync selected GitHub Actions secrets to AWS Secrets Manager using GitHub OIDC, an AWS IAM role, Terraform, and a Python script.

The goal is simple: GitHub keeps the source values, AWS receives a JSON secret, and no long-lived AWS access key is stored in GitHub.

## How It Works

1. Terraform creates the AWS Secrets Manager secret, the GitHub OIDC provider, and an IAM role.
2. The IAM role trusts only the configured GitHub repository and branch.
3. A manually triggered GitHub Actions workflow assumes that role through OIDC.
4. The workflow passes selected GitHub secrets to `scripts/sync-secrets.py`.
5. The script writes a new JSON version to the AWS secret.

Terraform manages infrastructure and secret metadata. The workflow manages secret values.

## Terraform Setup

Create a local `infra/terraform/terraform.tfvars` file based on the example:

```hcl
github_oidc_subject = "repo:YOUR_USERNAME@OWNER_ID/YOUR_REPOSITORY@REPO_ID:ref:refs/heads/main"
```

The subject must match the GitHub OIDC token `sub` claim exactly. The current example assumes:

- repository workflow running from `main`
- no GitHub Environment
- IAM trust restricted to one exact subject

Then provision the infrastructure:

```bash
cd infra/terraform
terraform init
terraform fmt -check
terraform validate
terraform plan
terraform apply
terraform output -raw secret_arn
```

To get the role ARN after applying:

```bash
aws iam get-role \
  --role-name role-sync-github-secrets \
  --query Role.Arn \
  --output text
```

If the AWS account already has a GitHub OIDC provider, import it into Terraform or adapt `oidc.tf` before applying.

## GitHub Actions Setup

Create these repository variables in **Settings -> Secrets and variables -> Actions -> Variables**:

| Variable | Description |
| --- | --- |
| `AWS_REGION` | AWS region where the secret exists |
| `AWS_ROLE_ARN` | IAM role assumed by the workflow |
| `AWS_SECRET_ARN` | Secrets Manager secret ARN from Terraform output |

Create these repository secrets in **Settings -> Secrets and variables -> Actions -> Secrets**:

| GitHub secret | AWS JSON key |
| --- | --- |
| `DEMO_API_TOKEN` | `api_token` |
| `DEMO_DB_PASSWORD` | `db_password` |

Run the workflow manually from **Actions -> Sync secrets to AWS -> Run workflow**.

## Secret Format

The destination value in AWS Secrets Manager is a JSON object:

```json
{
  "api_token": "value from DEMO_API_TOKEN",
  "db_password": "value from DEMO_DB_PASSWORD"
}
```

Each workflow run writes a complete new version of the secret. Existing JSON keys that are not generated by the script are not preserved.

To add another value, update both places:

- the `env` mapping in `.github/workflows/sync-secrets.yml`
- the `SECRET_FIELDS` mapping in `scripts/sync-secrets.py`

## Validation

The script fails before writing to AWS when:

- `AWS_REGION` is missing
- `AWS_SECRET_ARN` is missing
- one of the required GitHub secrets is missing or blank
- the generated JSON is larger than the AWS Secrets Manager limit

The workflow does not print secret values. AWS errors are reported without dumping exception details into logs.

## Git Rules

Commit:

- Terraform source files
- `.terraform.lock.hcl`
- `.gitignore`
- workflow and script files
- `terraform.tfvars.example`

Do not commit:

- `.terraform/`
- `terraform.tfstate`
- `terraform.tfstate.backup`
- `terraform.tfvars`
- Terraform plan files
- local `.env` files

## Cleanup

The example secret uses `recovery_window_in_days = 7`, so deletion is not immediate. Review the Terraform plan before destroying resources:

```bash
cd infra/terraform
terraform destroy
```
